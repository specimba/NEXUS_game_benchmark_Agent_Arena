# NEXUS Agent Arena review — repository + PR #8 + new game-benchmark literature

I checked the live repository, PR #8, its prompt lineage, rubric, anti-gaming layer, evidence schema, aggregator, launcher, long-session protocol, Round 012 findings, and the new paper set you supplied. The uploaded paper packet matches the current primary-paper records for RLHEV, GameEngineBench, and GameXpert-Bench. 

My conclusion is:

> **The core NEXUS idea is stronger than most current game-agent benchmarks: an open-ended creator arena judged as a finished interactive product. But the project has reached the point where “battle prompt evolution” and “benchmark science” must become two separate layers.**

PR #8 is a major empirical research archive—28 changed files, 1,571 additions, prompt lineage v10→v18, controlled experiments, cluster analysis, and R007–R012 fold-backs.  But I would **not merge it as the final benchmark control plane yet**, because the evaluator machinery has fallen behind the prompt/rubric evolution.

# 4. The current benchmark is actually **two different scientific instruments**

This is the biggest structural insight from comparing NEXUS with GameXpert, GameDevBench, GameEngineBench and OpenGame.

Your existing benchmark asks:

> Give two agents the same very open creative brief. Which one creates the better game?

That is excellent for:

```text
PRODUCT QUALITY
creative judgment
authorship
scope decisions
taste
engineering under ambiguity
```

But it is weak for diagnosing:

```text
why model X failed
whether model X understands collision
whether harness Y improves debugging
whether model Z preserves regressions
```

because every agent chooses a different task for itself.

This is an **arena**, not a controlled task benchmark.

And that's fine.

Do not destroy that uniqueness trying to imitate the papers.

Instead make:

```text
NEXUS AGENT ARENA
        │
        ├── ARENA MODE
        │    open creation
        │    human preference
        │    authorship
        │
        └── BENCHMARK MODE
             fixed tasks
             executable tests
             lifecycle diagnosis
```

# 5. GameXpert-Bench gives us the missing lifecycle structure

GameXpert-Bench is the most directly useful new work for your repository.

It explicitly splits game-agent capability into:

| Track       | What happens                                        |
| ----------- | --------------------------------------------------- |
| **GameGen** | empty workspace → complete game                     |
| **GameFix** | defects → diagnose + repair                         |
| **GameOpt** | playable game → six cumulative improvement requests |

It contains 97 generation tasks, 100 repair tasks derived from 50 human-verified game levels with 19–27 injected defects per level, and 17 six-turn optimization chains / 102 requests. GameFix uses Fail-to-Pass and Pass-to-Pass regression gates; GameOpt contains 701 acceptance criteria. ([Kun Chen][1])

The central result is almost exactly what we've observed informally:

> Agents are considerably better at producing plausible/playable foundations than at **discovering defects, verifying runtime behavior, and preserving prior functionality during changes**. ([arXiv][2])

Your Round 012 already hints at this: PRISMA became exceptional partly because the agent caught and repaired four bugs itself.

So make that capability measurable instead of anecdotal.

# 6. Proposed **NEXUS Agent Arena 2.0 track architecture**

I would define five independent tracks.

| Track                 | Purpose                                   | Primary evidence                                  |
| --------------------- | ----------------------------------------- | ------------------------------------------------- |
| **A — OPEN-CREATIVE** | Current flagship one-shot battle          | Human jury + hard runtime gates                   |
| **B — FIXED-GEN**     | Same task across agents                   | Hidden behavioral tests + jury                    |
| **C — REPAIR**        | Find/fix seeded defects                   | Fail-to-Pass + Pass-to-Pass                       |
| **D — OPTIMIZE**      | Multi-turn enhancement without regression | cumulative acceptance + regression                |
| **E — SIM-FIDELITY**  | Physics/world/simulation correctness      | engine invariants + repeated-rollout distribution |

Never combine these into one opaque “agent score.”

An agent can be:

```text
excellent OPEN-CREATIVE
average FIXED-GEN
excellent REPAIR
poor OPTIMIZE
excellent SIM-FIDELITY
```

That tells us something useful.

# 7. Track B: borrow from GameDevBench and GameEngineBench

**GameDevBench** now has 333 Godot tasks and explicitly evaluates model + harness, including screenshot and runtime-video feedback. Its current repository reports that visual feedback raised GPT-5.4 from 41.1% to 52.0%. ([GitHub][3])

**GameEngineBench** moves this further into UE5/C++: 110 scoped tasks from nine real projects, spanning gameplay, multiplayer, AI/world orchestration, animation, sessions, persistence, serialization, XR and rendering plugins. The strongest evaluated configuration reaches 55.5% pass@1 and 31 tasks remain unsolved across all twelve configurations. ([arXiv][4])

This suggests a new fixed-generation / modification shelf for NEXUS.

Not necessarily Godot or Unreal.

For our browser arena, use browser-native fixed tasks such as:

```text
implement an articulated crane with real pendulum response
complete an opponent AI with three behavioral states
add a deterministic projectile system
repair a broken WebGPU fallback
implement a multi-stage state machine
add a save migration
add collision + moving-platform behavior
build a responsive HUD without altering game rules
```

Now different agents solve **the same engineering problem**.

That gives us diagnostic capability the open creative battle deliberately lacks.

Your current fairness contract says identical prompt + equal time.

That is necessary.

So label runs:

```text
SYSTEM_BATTLE
natural model + native harness + available tools

MODEL_CONTROL
same harness/tool environment, different model

HARNESS_CONTROL
same model, different harness
```

This is extremely valuable for your broader NEXUS research because it can tell us:

```text
Did Gemini win?
or

Did Claude improve?
or
Did runtime-video access improve?

Did GPT fail?
or
did its harness never expose the screen?
```

Do not force every battle into MODEL_CONTROL.

Just stop calling a SYSTEM_BATTLE a pure model comparison.

# 10. RLHEV gives us a new **engine-verifier plane**

Your supplied source correctly summarizes the paper's central idea: game engines provide executable checks for collision, physics, navigability and bounded playability, while human acceptance provides a broader semantic signal. 

The primary paper explicitly frames RLHEV as combining dense engine feedback with human acceptance. ([arXiv][7])

This maps beautifully to NEXUS:

```text
GAME ARTIFACT
      │
      ├── deterministic verifier
      │      collision
      │      state invariants
      │      goal reachability
      │      physics legality
      │
      ├── behavioral verifier
      │      input sequence → expected state
      │
      └── HUMAN JURY
             fun
             authorship
             coherence
             surprise
```

Neither plane replaces the other.

And this means our current jury should **not be responsible for discovering every machine-checkable fact**.

Humans should judge the things machines cannot reliably prove.

# 11. PAWBench adds a dimension our benchmark currently almost entirely misses

PAWBench fixes the starting state and action and repeats the rollout **50 times** to evaluate the model-induced distribution of possible futures. It explicitly reports calibration and support coverage separately rather than collapsing them into one score. ([PAWBench][8])

It also reports readout failures separately and requires at least 20 readable outcomes from 50 rollouts before a scene is scoreable. ([PAWBench][8])

That is exactly what we need for games claiming:

```text
physics
fluid simulation
procedural ecology
economics
emergent AI
stochastic world dynamics
```

A single pretty run proves almost nothing.

For those entries:

```text
fixed initial state
fixed input sequence
      ↓
N repeated runs
      ↓
outcome distribution
```

Evaluate separately:

```text
Invariant pass rate
Outcome support coverage
Distribution calibration
Readout/runtime failure rate
```

This should be **optional Track E**, not required from a narrative game.

# 13. The current 60-minute evaluation protocol needs one important repair

Your present S4 requires:

> 60 minutes continuous play, no restart,

and high flow scores effectively depend on long play.

This works for roguelikes/endless games.

It is unfair to an intentionally excellent **12-minute complete game**.

A short designed work should not be forced to provide 60 minutes of content.

Split S4:

```text
S4-RUNTIME-SOAK
60 minutes
technical only:
memory
jank
state corruption
performance

S4-EXPERIENCE-ARC
complete intended arc
then repeats / alternate paths
engagement scoring
```

For short games:

```text
12-minute game
→ full run
→ 2–3 repeated runs / alternate paths
→ separate runtime soak
```

For long games:

```text
60-minute natural play
```

This separates:

```text
runtime longevity
≠
designed content duration
```

and avoids bias toward endless procedural games.

* whether the agent iterated;
* whether it debugged;

Make two objects:


```text
DevelopmentProcessReceipt
```

Artifact quality includes:

```text
reliability

flow
```


Never let process narrative rescue a bad artifact.

# 18. v18's engineering ideas are good—but over-generalized

v18 adds:

* real-domain-number research;
* fixed module ownership;
* exact data interface contract;
* fixed-step simulation;
* zero top-level side effects;
* seeded randomness only;
* durable state ≠ transient event;
* no hot-loop allocation;
* presentation cosmetic only.

They came from a thoughtful Claude-of-Tanks analysis.

I strongly support the **engineering philosophy**.

I do not support imposing all six invariants on every open creative game.

A turn-based narrative mystery does not need a 60 Hz simulation.

A CSS spatial puzzle does not necessarily need a simulation/render authority distinction.

A deterministic authored narrative may not need seeded RNG.

A tiny elegant game does not need a module contract.

So make them conditional:

```text
IF continuous simulation:
  simulation independent from presentation timing

IF randomness affects outcomes:
  make runs reproducible or record the seed

IF multiple subsystems exchange state:
  define their interfaces before integration

IF claiming real-world simulation:
  ground relevant constants/ranges

FOR EVERY GAME:
  test the riskiest core rule directly before delivery
```

This retains the Claude-of-Tanks lesson without converting the benchmark into:

> “who best imitates Claude-of-Tanks architecture?”

# 19. Candidate **Battle Prompt v19 CORE**

I would create this as a **held experimental arm**, not overwrite v17/v18 immediately.

Run v17/v18/v19 under a controlled same-model/harness experiment first.

Here is the version I would test:

# BATTLE PROMPT — Build one excellent browser game in one sustained session (v19 CORE candidate)

You have one sustained development session to create a complete, original, playable browser game.

Your goal is not to demonstrate a framework, imitate a genre, maximize feature count, or satisfy a hidden aesthetic formula. Your goal is to make an interactive experience that a real player would choose to keep playing.

Before writing code, answer privately:

**Why does this idea need interaction rather than merely being an animation, illustration, or story?**

Do not automatically build the first concept that comes to mind. Briefly consider a few materially different possibilities, then choose the one with the strongest combination of:

* meaningful player action;
* room for mastery, discovery, tension, consequence, or expression;
* a scope you can finish;
* an identity you can sustain across the entire game.

Do not include those discarded concepts in the deliverable.

## Creative freedom

The format is your decision.

Use the genre, dimensionality, camera, rendering method, visual style, input model, narrative structure, simulation depth, and technical stack that best serve your game.

A sophisticated game does not need to be 3D. A technically complex game does not receive credit merely for being complex. A minimal game can be excellent if the constraint feels deliberate and the execution is unusually strong.

Aim for contemporary craft appropriate to the direction you choose. Default-template presentation, placeholder geometry, generic UI, or spectacle that does not improve the experience will not make the game stronger.

If visual ambition matters to your concept, choose and execute a coherent visual strategy—lighting, materials, texture, animation, composition, atmosphere, typography, effects, procedural detail, authored assets, or another approach appropriate to your stack. Choose the technique yourself.

## Build loop

Do not spend the entire session planning, and do not stop at the first version that runs.

Get the smallest real playable loop working early.

Then repeatedly:

**play → observe → identify the most important weakness → repair or improve it → play again**

Use the actual running game as evidence.

Prioritize defects that affect the player before adding breadth.

If a system is complex enough that integration mistakes are likely, define its important ownership and data boundaries before wiring it together.

If continuous simulation determines gameplay outcomes, keep gameplay state independent from rendering speed.

If randomness materially affects outcomes, make a run reproducible or record the seed.

If your concept claims meaningful real-world behavior, use defensible ranges or data rather than arbitrary numbers where that matters.

Before delivery, directly test at least one of the core rules most likely to be wrong.

## Minimum finished-game contract

The final game must:

1. **Launch cleanly.** A fresh load reaches a coherent playable entry state without a blank screen, fatal missing asset, infinite loading state, or repeating console-error failure.

2. **Contain a real interactive loop.** The player's actions must change what happens. There must be meaningful resistance, consequence, uncertainty, trade-off, discovery, failure, commitment, or another force that prevents the experience from being passive autoplay.

3. **Teach itself through play.** A new player should understand enough to begin without reading the README and should reach a meaningful consequence or progression beat early in the experience.

4. **Have reliable controls and state transitions.** Real mouse, keyboard, and any claimed touch controls must work. Menus must not leak actions into gameplay. Restart must return the game to a valid initial run state.

5. **Pause outcome-affecting gameplay correctly.** Gameplay simulation, timers, spawning, AI, physics, or other outcome-producing state must not continue unintentionally while paused. Cosmetic menu animation may continue if it cannot change game outcomes.

6. **Provide immediate audio control if audio exists.** Muting must become perceptibly effective immediately and must prevent new game audio until unmuted. Audio initialization failure must not make the game unplayable.

7. **Survive ordinary browser boundaries.** Resize, tab blur/focus, visibility changes, repeated input, and malformed local persistence data must not destroy the run where those surfaces apply.

8. **Remain readable.** Visual effects must return the playfield to a usable state after transient flashes, transitions, hits, explosions, or post-processing effects.

9. **Be self-contained.** The delivered player experience must run without runtime telemetry, analytics, hidden reporting, authentication, or required external network services. Bundle the resources needed to play.

10. **Be honest.** Do not ship placeholder interactions, dead controls, unreachable claimed features, a cinematic autoplay presented as gameplay, or documentation that describes functionality the delivered build does not contain.

## Ambition and scope

Ambition is valuable only when it survives actual play.

If an ambitious rendering, simulation, procedural, AI, or physics path is unstable near delivery, simplify it until the finished game is coherent.

A smaller game that is expressive, deep enough for its intended duration, and reliable is stronger than an impressive screenshot attached to a broken game.

The experience should not exhaust its complete idea immediately after the first visual or mechanical surprise. Give the player another meaningful beat: a changed decision, deeper interaction, escalation, new relationship, altered environment, emergent consequence, or other development appropriate to your design.

## Final verification

Before delivering, run the game from a fresh load and verify:

* entry state appears correctly;
* real controls behave as intended;
* the main interactive loop works;
* at least one meaningful adverse/consequence path works;
* restart fully resets the run;
* pause does not change gameplay outcomes;
* mute works if audio exists;
* resize and blur/focus recover cleanly;
* no persistent unreadable visual effect remains;
* the most technically ambitious path you actually ship works end-to-end.

Fix failures you can. Remove or disclose anything you cannot honestly finish.

## Deliverables

Deliver:

* the complete runnable game;
* source required to run it;
* a short `README.md`.

The README must begin with either:

`TRACK: strict-one-shot`

or

`TRACK: iterated (N passes)`

Then include:

* how to run;
* controls;
* major stack/runtime choices;
* locally bundled generated or externally sourced assets and their provenance;
* important features intentionally cut;
* known limitations;
* `WHY_INTERACTIVE`;
* `DESIGN_PILLARS`;
* `HONEST_SELF_ASSESSMENT`.

Do not include benchmark scores or predictions about how judges will rate the game.

Deliver the strongest complete game you can make within the session.

This keeps almost all of the useful v16–v18 learning while removing the largest prompt attractors.

The pipeline:

```text

      ↓
```

# 29. Immediate sequence I recommend

The next work should happen in this order:

1. **Do not expand PR #8 further conceptually.**
2. Repair the scorer/schema/rubric desynchronization.
3. Add CI tests that fail if criteria, weights or ceilings drift.
4. Merge PR #8 as the historical v10→v18 evolution packet.
5. Open a new **Agent Arena 2.0** PR.
6. Add v19 as a **held experimental prompt**, not live.
7. Run v17/v18/v19 controlled prompt ablation.
8. Add Repair track.
9. Add Optimization track.
10. Add Simulation Fidelity as an optional specialized track.

The new papers support this division strongly: GameXpert says lifecycle matters, GameDevBench/GameEngineBench show executable engine tasks expose agent weaknesses, RLHEV shows engine verification can become dense trajectory evidence, PAWBench shows one attractive rollout is not a world model, and OpenGame shows whole-game generation needs both runtime health and intent/visual assessment. ([arXiv][2])

### My final assessment

The unique thing worth protecting is **not the current 0–100 rubric**.

It is this:

> **NEXUS Agent Arena studies an AI developer under creative freedom, records how prompt/harness conditions shape what it chooses to build, then subjects the resulting executable artifact to independent product, engineering, regression, and eventually simulation evidence.**

That is substantially more interesting than another coding leaderboard.

The next version should therefore become:

```text
OPEN CREATIVE ARENA
        +
FIXED EXECUTABLE TASKS
        +
REPAIR
        +
MULTI-TURN REGRESSION
        +
SIMULATION FIDELITY
        +
MODEL × HARNESS PROVENANCE
```

while keeping each evidence plane separate rather than hiding everything inside one score.

I would treat **scorer/schema synchronization as the immediate blocker**, and **v19 + lifecycle tracks as the next research epoch**.
